# Quantum Light Follow-ups: graduate implementation skeleton

This folder is a structured graduate assignment for completing **Project A** and **Project B** in `quantum_light_followups.pdf`. It is designed for learning through derivation, implementation, numerical verification, and discussion—not for generating a finished project in one step.

**Recommended repository name:** `quantum-light-followups`.

## Start in this order

1. Read [`LEARNING_GUIDE.md`](LEARNING_GUIDE.md), including the instruction labels and strict process rules.
2. Read the project note, `quantum_light_followups.pdf`, to understand the physical goals and proposed models.
3. Open [`MILESTONES.md`](MILESTONES.md) and work on **only the current milestone**. It lists concrete tasks, required and related reading, deliverables, and the meeting gate.
4. Read the instruction comments in the skeleton code before implementing each function.
5. Meet Marcelo after every milestone. Do not continue to the next milestone until the derivation, implementation, tests, and open questions have been discussed.

## Instruction labels

- **`REQUIRED`**: mathematical, physical, verification, or process constraints that must be satisfied.
- **`GUIDED`**: a recommended starting route; a justified equivalent alternative is allowed.
- **`OPEN`**: an open implementation or research choice for the student.
- **`THINK`**: a question to answer in the student's own words, supported by the derivation and literature.
- **`CHALLENGE`**: an optional improvement after the required version works; stronger claims need stronger evidence.

The instructions are not perfect rules and are not guaranteed to represent the best possible implementation. Students may identify weaknesses, choose a better representation, improve an algorithm, or challenge a claim—but must document the reason, verify the alternative, and discuss it at the milestone meeting.

## Skeleton code

The code is intentionally incomplete. Functions with `NotImplementedError` are tasks for the student, not finished routines.

- `code/majorization.py`: POVM conventions, Lorenz curves, majorization, entropy measures, analytic-bound tasks, sampled-state optimization, and the operator-level solver.
- `code/project_a.py`: detector effects, Fock-space blocks, Monte Carlo counts, detector mismatch, non-attainment gap, and steering.
- `code/project_b.py`: binned quadratures, clock/shift matrices, Zak/GKP-related blocks, overlap and energy constraints, homodyne loss, binning bias, optical states, and EPR steering.
- `code/verify_bounds.py`: a test harness and milestone-specific verification tasks, with no prewritten answers.
- `code/make_figures.py`: figure tasks that must use data generated by the student's implementation.
- `code/requirements.txt`: basic numerical dependencies only. QuTiP and other project-specific libraries are optional future choices, not preinstalled assumptions.

Do not replace `NotImplementedError` with a numerical value copied from the PDF. Reproduce a target only by deriving the model, implementing the calculation, and testing it independently.

## Reference text and reading material

- `quantum_light_followups.pdf`: the project specification and proposed research directions.
- `paper/main.pdf` and `paper/main.tex`: the current reference manuscript.
- `paper/quantum_optics_future.md`: optical background and the former open question on light modes, reserved for Project B.
- `paper/references.bib`: bibliography cited by the manuscript and optical material.
- `paper/revision_notes.md`: examples of how analytical results, numerical observations, and presentation decisions were distinguished in the reference manuscript.
- `paper/figures/`: reference figures for scientific context, not data files to copy into new results.

## Nine milestones

1. Baseline, literature, and reproducibility.
2. Project A: single-photon detector model.
3. Project A: Fock-space and multi-photon model.
4. Project A: Monte Carlo virtual experiment.
5. Project A: Lorenz gap, detector maps, and steering.
6. Project B: binned quadratures and the Zak/GKP reduction.
7. Project B: overlap map and energy-constrained overlap.
8. Project B: loss, binning bias, and optical applications.
9. Independent review, reconstruction, and writing.

Each milestone has its own reading list, implementation tasks, deliverables, open questions, and a required meeting with Marcelo in `MILESTONES.md`.

## Use of AI

AI may help explain a concept, review a small derivation, suggest a test, or debug a limited piece of code. It must not replace the student's derivation, implementation, verification, or scientific judgment. Keep a short record of what AI suggested, what was accepted or rejected, and what was independently checked.

The objective is not to finish as quickly as possible. The objective is to be able to defend every model, every line of code, every figure, and every claim during the milestone meetings.
